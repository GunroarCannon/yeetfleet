# Playtest feedback batch — decisions

| Decision | Choice | Why | Revisit when |
|---|---|---|---|
| Massive-hit detection | `FlightModel.collided(closing, other_radius, other_kinematic)`; massive = `other_kinematic and other_radius > 25.0` | Rocks stay under 25m; planets/stations/anomalies are all far above it | a scenery type blurs the line (e.g. a 20m kinematic prop that should count) |
| Crash camera reaction | Scale `FlightCamera.bump_zoom`'s pull-back way up for massive hits (`BUMP_ZOOM_PULLBACK_MASSIVE`) and slow its decay so the recovery reads as a tween, not a snap. No new camera mode, no hard ship-position "insurance" snap. | User's read: the break is a camera-easing problem, not a physics-penetration problem — the fix stays entirely camera-side | if the ship is still visibly embedded after this, revisit whether physics separation itself is too slow |
| Emote system | Not a mounted sticker at all. A one-shot billboard that pops out from the ship, shoots outward, fades, and frees itself — triggered by events only | User's explicit correction: "it should be an emote... shoots out and fades away to get destroyed" | never — this replaced the original recommendation outright |
| Emote idle behavior | No idle/default face — only event-triggered pop-outs exist | User: "There should be no face since there would be no emote" | if a later pass wants a resting expression back |
| Emote icon set | Reuse existing face PNGs for now, but keep the spawner texture-agnostic — user plans to add non-face icons (exclamation marks, etc.) later | User: "Emotes can also be exclamation marks and stuff that I may replace with actual drawings" | when new icon art lands |
| Ramming damage scaling | Bump existing coefficients in `_apply_collision_damage` (base_dmg 2.5→3.5, >25.0 branch multiplier raised) rather than a parallel formula, further scaled by a new `JuiceSettings.ram_damage_mult` dial | Keeps one tuned formula; the extra multiplier satisfies "manage it from the flight test" | if speed-scaling still feels too linear after playtesting |
| HP / TTK reduction | New `JuiceSettings.hull_hp_mult` (default 0.65) applied to hull HP lookups; `JuiceSettings.player_durability_mult` (default 1.8) replaces the hardcoded ×2.5 in `_durability()` | Explicit ask: lower HP everywhere, tunable live ("managed in the flight test") | after a balance pass settles a final number |
| Popcorn enemies | Dedicated `popcorn: bool` on weak archetypes in `ai_factions.gd`; gated globally by `JuiceSettings.popcorn_enemies_enabled` | Explicit flag over a derived threshold — clearer, directly toggleable for testing | if more granular tiers are wanted later |
| AI forward-positioning | New `JuiceSettings.ai_flank_enabled` + `ai_flank_chance_mult` (scales base 85% PURSUIT/ENGAGE, 20% FLEE chances, rolled once per state-entry); blends steer target toward a point ahead of the player along the player's forward vector; FOV test is a plain dot product | Explicit numbers from the user (85/20, up from my 65/20 recommendation); toggle/dial home matches `collision_bump_zoom`'s precedent | if AI reads as too "psychic" at 85% |
| Aim assist | Crosshair magnetism only (nudge aim toward the lead-reticle point when already close), not widened hit-forgiveness. Exposed as `JuiceSettings.aim_assist_enabled` + `aim_assist_strength` | User accepted; keeps assist an input-side nudge instead of a hidden fudged hitbox | if magnetism alone doesn't read as "more assist" |
| Persistence convention | Every new gameplay dial from this batch lives on `JuiceSettings` (bool via the existing `set_effect` dispatch, floats via small dedicated setters), persisted to `user://juice.cfg`, surfaced in `combat_settings_modal.gd`'s "Juice & Feel" section | User: "all the dial settings should save over games, so one can actually edit THE Game inside THE game" — `JuiceSettings` is the project's existing home for exactly this kind of persisted, individually-toggleable combat/feel knob | if a dial needs to be per-design rather than global |
| Crash / hit camera (round 2, **supersedes** the bump-zoom row above) | One dynamic zoom for weapon hits and crashes: a critically damped spring toward a target that holds, then slides back. Scales the smoothed chase offset (plus FOV), never fed into the follow smoothing. Knockback absorbed by a physics-tick-aligned follow lag. Tumbling hull spins inside a slow-drifting frame. Boost release eased. Camera smoothing runs on real time so hitstop doesn't stall it | User: the old zoom "is stuck… forced back immediately"; "anything forcing the camera… should chill until the camera is done being dynamic, then tween back" | if the zoom reads as floaty — shorten `cam_zoom_out_time` / `cam_zoom_hold` first |
| Juice dial home | A dedicated 🎬 Juice chip on the flight HUD top bar, next to the art-style chip, opening `JuiceSettingsPanel`. The juice/balance rows moved out of the combat modal | User asked for it by name | if the top bar gets too crowded on mobile |
| Shot-sound interval | Per-shooter gate: the next shot sound is due `pct`% of the sound's (pitch-adjusted) length after the last one started. Default on at 100% (back to back). **Assumed**: 0% or below plays every shot (the old behaviour), since the user gave −200..200 without saying what negative means | Explicit ask with explicit default and range | when the user says what negative percentages should do |
| AI pacing | Burst (1.2–2.2 s) / rest (1.6–3.2 s × `ai_rest_mult`) rhythm, and at most `ai_max_attackers` (default 3) ships firing at the player at once via expiring shared slots. Ship-vs-ship fights keep the rhythm but skip the slot cap | "Bombard the player endlessly" → attack tokens are the standard fix; the cap is a dial | if fights feel too sparse — raise the cap before shortening rests |
| Flanker speed match | A flanker already in the player's forward cone faces the player and throttles to hold a 260 m standoff: backs off at the player's closing speed, reversing down to the flight model's −0.35 lever limit | User: "adjusting their velocity to be slower or even backwards" | if they still get overrun at boost speed — the reverse limit is the cap |
| Hit/shield effect budget | Hull-hit effects moved onto the hull surface facing the shot, scaled by `hit_vfx_scale` (default 0.5), rate-limited to one every 120 ms. Shield flash on its own `shield_fx_intensity` (default 0.35, 0 = off), rate-limited harder at low intensity | Screenshot: explosions whiting out the screen; "forcefield too much per hit… controllable, to save CPU" | — |
| Physics interpolation (round 3, user: "yes, and toggleable") | On by default, toggled in the ⚡ Performance panel (`SceneTree.physics_interpolation`). Only physics-moved things opt in: the player's FlightModel, AiShip, debris bodies. FlightRoot switches it off for its own subtree (camera, sky, HUD, emotes, effects are placed per frame). The camera reads `get_global_transform_interpolated()`. Teleports are caught by FlightModel's jump detector, not by each caller | Measured at 144 fps: steady-flight camera stepping 2.12 → 0.002 m/frame² | if some other per-frame-moved node appears inside a ship's subtree |
| Time-scale ownership | FlightRoot writes `Engine.time_scale = warp × death slow-mo × Juice.hitstop_factor()` each frame. JuiceRuntime times hitstop in real ms | FlightRoot used to write the warp alone every frame, cancelling hitstop and death slow-mo a frame after they began. That one-frame hiccup was the "jerk" on hits | — |
| Performance settings | New core `PerformanceSettings` (persisted to `user://performance.cfg`), with a ⚡ Perf chip and panel. Frame cap, V-Sync, physics rate, interpolation, render scale, MSAA, FXAA, mesh LOD, shadows, glow, AI cap, effects budget, debris cap/lifetime. Three presets: "Smoothest" = every dial at its cheapest | User: "if all set to high game should be running very smoothly" | if a world-detail dial should move here from Settings |
| Settings persistence | Control mode, assist mode, chase/cockpit/rear view and render distances added to Session. FlightRoot mirrors live state into Session and runs a change-detecting `Session.autosave()` every second and on exit. Autosave is skipped headless, so smoke tests can't overwrite player settings | Control mode had never been in Session at all, and several setters never saved | — |
| Part loss & explosions | AI ships reuse `DamageSystem`: a part comes off at each third of HP lost (plus a small random chance), with the same flight effects as the player's, and a lost gun cuts fire power. Every lost part explodes. `AddonVfx.explosion` / `nuke` bypass the effects budget | "All ships that are destroyed should go out with explosion, including when they just lose a part". The budget could silently skip death explosions | if part loss feels too frequent — lower the random-chance term first |

## Open / deferred
- Smoke tests that change settings through explicit `Session.save_to_disk()` setters still write the real `user://session_settings.cfg`. This predates this batch; autosave no longer adds to it.
- Laser sound softening (pitch/volume jitter + high-frequency taming) and the tumble-to-"spinning top" simplification are tuning passes on existing systems — no open decisions, routed straight to implementation.
- Kill-detection signal for the emote system's grin/happy trigger — wiring detail, not a decision; resolved during implementation by reading how AI death is currently reported.
